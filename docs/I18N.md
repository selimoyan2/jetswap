# JetSwap Internationalization (i18n) & Global App Shell Guide

## 1. Architecture Overview

JetSwap is engineered as a **Global Barter Network**. The internationalization architecture is designed to scale across dozens of languages while ensuring type safety, zero layout shifts, SEO compatibility, and strict non-translation of user-generated content (UGC).

### Core Components

```
src/
├── i18n/
│   ├── config.ts              # Supported locales, text directions, cookie/storage constants
│   ├── types.ts               # TranslationSchema interface (contract for all dictionaries)
│   ├── helpers.ts             # Status, condition, trade method, and date formatters
│   ├── index.tsx              # LanguageProvider, useLanguage hook, persistence
│   └── locales/
│       ├── tr.ts              # Turkish dictionary (Canonical reference)
│       ├── en.ts              # English dictionary (1:1 Key parity with tr.ts)
│       └── index.ts           # Central dictionary registry
├── components/
│   └── shell/
│       └── global-app-shell.tsx # Universal App Shell (Navbar, Main, Footer, BottomNav)
└── middleware.ts              # Next.js Edge Middleware for SEO prefix rewrites
```

---

## 2. Global App Shell Pattern

To guarantee that customer-facing pages never miss the global navigation or footer, the application shell is centralized in `src/components/shell/global-app-shell.tsx` and wrapped inside `src/app/layout.tsx`:

- **Admin Isolation**: Pages starting with `/admin` automatically bypass customer shell elements (Navbar, Footer, MobileBottomNav).
- **Zero Duplicate Footers**: Internal pages (`/offers`, `/favorites`, `/saved-searches`, `/notifications`, `/jetmatch`, `/items/[id]`) do not render redundant footers or navigation bars.
- **Server Cookie Hydration**: `src/app/layout.tsx` reads the `jetswap_locale` cookie on the server and passes `initialLocale` directly to `LanguageProvider`, eliminating client-side hydration flash.

---

## 3. SEO Locale Routing & Edge Middleware

- **Canonical URLs**: Both standard URLs (`/offers`, `/jetmatch`) and localized URLs (`/en/offers`, `/tr/offers`) are supported out of the box.
- **Next.js Rewrite**: The Edge Middleware (`src/middleware.ts`) detects locale prefixes (`/tr/`, `/en/`) and rewrites the request internally to base routes (`/offers`) with the `x-jetswap-locale` header. No route files need to be duplicated under `[locale]/...`.
- **Cookie Persistence**: When a user switches language in the UI, `jetswap_locale` cookie and `localStorage` are updated simultaneously.

## 4. Status & Domain Enum Formatting

**Rule: Never display raw database enum strings (e.g., `COMPLETED`, `PENDING`) directly to users.**

Always use the centralized helpers from `@/i18n/helpers`:

```tsx
import { useLanguage, getOfferStatusLabel, getItemConditionLabel, getTradeMethodLabel } from '@/i18n'

export function MyComponent({ offer, item }) {
  const { language } = useLanguage()

  return (
    <div>
      {/* Localized offer status badge */}
      <span>{getOfferStatusLabel(offer.status, language)}</span>

      {/* Localized item condition */}
      <span>{getItemConditionLabel(item.condition, language)}</span>

      {/* Localized trade method */}
      <span>{getTradeMethodLabel(item.tradeMethod, language)}</span>
    </div>
  )
}
```

### Supported Prisma Enums:
- `TradeOfferStatus`: `PENDING`, `COUNTER_OFFERED`, `ACCEPTED`, `REJECTED`, `CANCELLED`, `COMPLETED`
- `ItemCondition`: `BRAND_NEW`, `LIKE_NEW`, `VERY_GOOD`, `GOOD`, `FAIR`, `REPAIR_NEEDED`
- `TradeMethod`: `HAND_TO_HAND`, `CARGO_ONLY`, `BOTH`

## 5. How to Add a New Language (e.g. German - `de` or Arabic - `ar`)

Adding a 3rd language is strictly type-checked and takes 4 simple steps:

### Step 1: Update `src/i18n/config.ts`
Add the language code to `SupportedLanguage` and register its metadata in `SUPPORTED_LOCALES`:

```typescript
export type SupportedLanguage = 'tr' | 'en' | 'de' | 'ar'

export const SUPPORTED_LOCALES: Record<SupportedLanguage, LocaleConfig> = {
  // ... existing tr and en ...
  de: {
    code: 'de',
    name: 'German',
    nativeName: 'Deutsch',
    flag: '🇩🇪',
    direction: 'ltr',
    dateFormat: 'de-DE',
    localeCode: 'de-DE',
  },
  ar: {
    code: 'ar',
    name: 'Arabic',
    nativeName: 'العربية',
    flag: '🇸🇦',
    direction: 'rtl', // RTL automatically supported!
    dateFormat: 'ar-SA',
    localeCode: 'ar-SA',
  },
}
```

### Step 2: Create the Dictionary File
Create `src/i18n/locales/de.ts`:

```typescript
import { TranslationSchema } from '../types'

export const de: TranslationSchema = {
  // TypeScript will enforce 100% complete key parity with TranslationSchema!
  // Any missing key will trigger a compile-time error.
}
```

### Step 3: Register in `src/i18n/locales/index.ts`
```typescript
import { tr } from './tr'
import { en } from './en'
import { de } from './de'

export const dictionaries = {
  tr,
  en,
  de,
}
```

### Step 4: Verify with the Automated Test Suite
```bash
npx tsx tests/i18n.test.ts
npx tsc --noEmit
```

## 6. RTL (Right-to-Left) Support

The i18n architecture is ready for RTL languages (`ar`, `fa`, `ur`, `he`).
When a language with `direction: 'rtl'` is selected:
- `LanguageProvider` automatically updates `<html dir="rtl">` on the document element.
- Tailwind CSS 4 logical properties (`ms-*`, `me-*`, `start-*`, `end-*`) ensure that spacing, padding, and alignments invert correctly without CSS overrides.

---

## 7. Strict UGC Invariant

> [!IMPORTANT]
> **User-Generated Content (UGC) is NEVER translated.**
> 
> Item titles (`item.title`), item descriptions (`item.description`), user offer notes (`offer.note`), barter chat messages (`message.content`), and user review comments (`review.comment`) represent personal authentic user intent. They must always be displayed verbatim.
